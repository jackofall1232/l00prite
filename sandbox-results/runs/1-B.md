- **Notes:** **Methodology correction mid-experiment, disclosed here for transparency.** The
  first attempt at this run used the literal mechanism specified in `task-specs.md` — instruct
  the Sonnet executor to call the Agent tool itself with `model: "opus"` before each substantive
  write — but that attempt made **zero** advisor consultations, because the Agent tool is not
  available inside a Workflow-spawned subagent's toolset in this environment (confirmed via the
  subagent's own exhaustive `ToolSearch` attempts). That attempt was **discarded as invalid**
  (it was functionally identical to a solo Sonnet run and would have contaminated the Arm B
  measurement) and the worktree was reset to the base commit before redoing this run. The
  redone version — used here and for every subsequent Arm B run — has the *orchestrating
  workflow script* broker three sequential agent calls: a Sonnet "planner" (writes a plan, no
  file writes), a real Opus 4.8 "advisor" (`model: "opus"` set directly by the orchestrator,
  reviews the plan, read-only), and a Sonnet "executor" (receives the plan and the advisor's
  actual feedback as context, then implements and commits). This is a genuine, verifiable Opus
  consultation — unlike the discarded attempt — but it is a coarser operationalization of "before
  every substantive write" than originally specified: it is one plan/advise cycle per task
  rather than one consult per individual file, since no mechanism was available in this
  environment for the executor to pause mid-implementation and re-consult in real time. For
  this task (a single-file change) the distinction is moot; it may matter more for Task 2. This
  deviation applies identically to all three Arm B runs for consistency and is also recorded in
  `sandbox-results/comparison.md`'s limitations section.
